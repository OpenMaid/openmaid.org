# Site plan

**Design:** `docs/specs/2026-11-21-site-design.md` (accepted 2026-11-21), cited below as "site §n". This plan keeps what
each milestone built, what it found, and where the build departs from the design. The design stays as accepted.

**Status:** milestones 1 and 2 built on 2026-11-21: milestone 1 on branch `feature/skeleton`, milestone 2 on
`feature/kamidori-database` after it; milestone 5's first three parts (§3 to §5) on `feature/kamidori-more-kinds`
after that; milestone 3, the reference pages (§6), on `feature/reference-pages` after that; milestone 5's fourth
part, the script relations (§7), on `feature/script-relations` after that; its fifth part, the languages (§8), on
`feature/languages` after that (2026-11-22); the design pass before publishing (§9) is under way on
`feature/design-pass` after that. The user chose milestone 1
as next ("Your call"), ahead of OME's export milestone 2, because the stack was the design's largest unverified choice.

## 1. Milestone 1: the skeleton, and the trial of the stack

### 1.1 What it built

- **The project:** Astro 7.4.13 with Starlight 0.43.1. Pagefind 1.6.0 comes with Starlight. It needs Node 22.23.4 or
  later; the trial ran on Node 24.11.1.
- **The guides** (site §7.1). `src/lib/ome.mjs` copies OME's `docs/modding/` from a local checkout into
  `src/content/docs/docs/`, which git ignores:
  - a guide's first `# ` heading becomes its title;
  - a `README.md` becomes its folder's index page.

  `astro.config.mjs` runs the copy each time the config loads, so `astro dev` and `astro build` both start from the
  checkout.
- **The sidebar** follows the guide index's "Where to go next" table, which is OME's reading order. The game guides
  form their own group. A guide the table does not name is listed after the table's, with a warning.
- **Link mapping** (site §7.1): `src/lib/guide-links.mjs`.
  - A guide's link to another guide goes to that guide's page.
  - A link to an OME file outside the guides goes to the file in OME's repository, at the checkout's commit. Nine
    links do: the generated global and patch-point references, and `adding-a-game.md`. Site milestone 3 maps the
    references to reference pages instead.
  - Any other relative link fails the build, naming the guide and the link.
- **Home** (site §6): `src/pages/index.astro`, built with Starlight's `StarlightPage`, so it shares the header, the
  search and the look. It holds:
  - what OME is;
  - the games, with their support levels and the maker's site, from the profile manifests;
  - a link to OME's latest release;
  - a line on the database to come.
- **The age notice** (site §8.10): `src/components/AgeNotice.astro`, placed in every page through an override of
  Starlight's `SkipLink`.
  - It is a dialog that the page opens already shown.
  - Its button closes it through `<form method="dialog">`, so it works without scripts.
  - With scripts the dialog is modal, and the confirmation is remembered in `localStorage` (`ome-age-confirmed`).
  - A head script marks a confirmed visitor before the first paint, so the notice never flashes for them.
- **The check:** `scripts/check-site.mjs` runs after every `npm run build` and exits 1 on any failure.
  - Every link and asset a page names on the site must resolve to a built file, and every anchor to an id on its
    page. This also checks the guides' anchors against the headings Astro actually built.
  - The search index must hold exactly the pages that mark their content for search.
- **`site.config.mjs`** (site §11 names it `site.config`). It holds:
  - the placeholder domain;
  - the checkout's path (`OME_CHECKOUT` overrides it);
  - OME's repository.

  It is JavaScript so that it can carry comments and read the environment.
- **The favicon** is a copy of OME's icon (`godot/assets/ome-icon.svg`, drawn for OME, MIT). Starlight links
  `/favicon.svg` from every page; the check found it missing.

### 1.2 The trial's results

The design's "not verified" items (site, header):

- **Versions.** Astro is at 7, as the research note said. One thing it did not foresee: Astro 7's Markdown processor
  is Sätteri, a Rust parser, not remark. A plugin is a Sätteri mdast plugin (`markdown.processor: satteri({
  mdastPlugins })`), and Starlight adds its own plugins to the same processor.
- **One project, one search index: verified.**
  - Starlight serves `/docs/`, and the home page is an ordinary Astro page.
  - Pagefind indexes every built page that marks its content for search, and `StarlightPage` marks it.
  - In headless Chrome, a search for a word only on the home page, typed into the header's search on a guide page,
    returns the home page. Guide words return the guides.
- **Scale.** A temporary route of 4,000 entity-like pages, each built with `StarlightPage` and a table of 24 linked
  fields, gave these numbers:
  - 4,018 pages built in 17.6 s, Pagefind's 3.3 s included;
  - 72 MB in 8,106 files;
  - the check walked 121,162 links.

  The route was removed.
- **File count (site §10.3).** Pagefind writes one fragment file per page, so the site has about two files per page.
  §10.3 estimated 5,000 files for Kamidori; it is nearer 8,000 before pictures, and three games pass Cloudflare's
  20,000 even with pictures on an asset host. The deploy milestone chooses the host with this number (§1.4).
- **The age notice in a browser.** Checked in headless Chrome:
  - on a first visit the notice is modal and nothing is stored;
  - Escape leaves it open;
  - the button removes it and stores the confirmation, and the next page has no notice;
  - with scripts off the notice shows, and its button closes it.

### 1.3 Found while building

- **Escape.** Chrome closes a modal dialog on Escape before the visitor has touched the page, whatever a `cancel`
  handler does. The first version took that close as a confirmation. Now only the button's value (`confirm`) counts,
  and a notice closed any other way opens again.
- **Starlight leaves a page out of search when its route ends in `/404`.** It takes such a page for a 404 page. The
  database's URLs end in the entity's slug (site §4), so an entity is affected only if its slug is `404`. Milestone 2
  must make sure no slug is `404`.
- **Data for a page goes through the virtual module `virtual:ome`.** In a built page, `import.meta.url` names the
  bundled chunk, not the source file, so a page cannot find the checkout by a relative path. The config resolves it
  and passes the pages what they read.
- **A failed build on Windows** sometimes ends with a libuv assertion from Node (`!(handle->flags &
  UV_HANDLE_CLOSING)`) after Astro's error. The build still fails, with Astro's message printed first.

### 1.4 Left for later, and why

- **Screenshots on the home page** (site §6). They show game art, so they wait for the user's word on which pictures
  the site's repository may hold.
- **The release's packages by name** (site §6). The checkout knows its version but not the latest release's assets.
  The home page links the latest release; the bundle or the release itself can name them later.
- **Support levels by name.** The manifests hold the codes (`P3`, `M3`), and the home page shows those and links the
  games page that explains them. If the bundle carries the levels' names (OME export §8.1), the home page can show
  them.
- **Where to buy** is the manifest's `launcher.site`, the maker's site. The manifests name no store.
- **Whether OME's repository is public** was not checked (`gh` is not installed here). If it is private at the deploy
  milestone, the nine links into it (§1.1) and the release link reach no one.
- **A header link to each section.** The site title links home, and the database does not exist yet. The header gets
  section links when the database's first pages do (milestone 2).

## 2. Milestone 2: Kamidori's first kinds

Built on 2026-11-21 on branch `feature/kamidori-database`, from OME's first export: Kamidori's 1,318 items, 445
units and 452 skills, game data revision `0294c8eafacf`. The user said "Go ahead".

### 2.1 What it built

- **Reading the export.** `site.config.mjs` `games` lists each game's revision. The export folder OME writes is copied
  to `data/<game>/`, which git ignores. `OME_SITE_GAMES` overrides which games are built; empty builds the site
  without a database.
  - `src/lib/export.mjs` reads the database with Node's built-in `node:sqlite` into the pages' model: kinds, fields,
    entities, references both ways, pictures and cells.
  - The build fails on a missing export, another format version, and a picture file the export lacks (site §10.2).
- **Pages** (site §4):
  - `/<game>/`, the game's front page;
  - `/<game>/<kind>/`, a list;
  - `/<game>/<kind>/<id>/<slug>/`, an entity;
  - `/<game>/tooltips/<kind>.json`, the tooltips;
  - `/pictures/<game>/<revision>/`, the pictures, with `standin/` for the blurred copies.

  Every database page is built on `StarlightPage`, with a sidebar of the game's kinds. The header links each section.
- **An entity page** (site §8.2) shows:
  - its name, pictures (a file used under two names is shown once), kind and game revision;
  - an infobox of its published fields;
  - its text;
  - what refers to it, grouped by kind and field;
  - script relations, once the export has them (§7);
  - the modder panel.
- **The infobox** reads values through `src/lib/values.mjs`:
  - a reference is a link with a tooltip;
  - an array's elements are named by the export's new `columns`;
  - a field at 0 or none goes in one line under the infobox;
  - an array whose elements are mostly 0 shows the others only.

  Without that, a key item's infobox was some forty rows of zeros.
- **The modder panel** (site §8.7) is in every entity page and shown only in modder mode. It names the record for OMS
  and data files (`unit[1]`, `[unit.1]`) and lists every cell a script wrote: its name as a data file writes it
  (`stats.max_hp`), its value, its writer (so its layer) and its address. It also lists the pictures' catalog names.
- **The explicit pictures** (site §8.11):
  - the build makes each stand-in with `sharp`, the picture shrunk to 12 pixels across and shown blurred at full
    size;
  - a click loads the picture;
  - the "Show explicit pictures" switch, beside modder mode's and remembered the same way, shows them all;
  - a thumbnail or a tooltip is never an explicit picture, and the site sets no preview image.
- **Lists** (site §8.3) have the rows in the page, filters on the export's filterable fields and the name, and the
  filters in the URL (`?race=3`).
- **Tooltips** (site §8.5): `public/tooltips.js` has no dependencies.
  - It shows the name, the thumbnail and a line of text, from the kind's file, loaded on the first hover.
  - On another site it shows the name and the picture only.
- **Search** (site §8.4) indexes an entity's name and text, with `game` and `kind` as Pagefind filters. Starlight's
  search box shows the filters by itself.
- **The 404 page** (`src/pages/404.astro`, in place of Starlight's) sends an entity's address without its slug, or with
  a wrong one, to the right page, using the kind's tooltip file.
- **`scripts/check-site.mjs`** also checks every entity the tooltip files list: its page is built and in the search
  index, and its picture is built.

### 2.2 Results

- **The build:** 2,237 pages in 15 s. Its output is 127 MB in 6,732 files, 45 MB of it pictures. The check walks
  59,993 links.
- **In headless Chrome:**
  - unit 331's page loaded only its stand-in until the click, then the picture;
  - the switch showed unit 52's explicit picture on load;
  - modder mode stayed on across pages;
  - `?race=3` showed 44 units;
  - `/kamidori/unit/331/` and `/kamidori/item/1/wrong-slug/` reached their pages;
  - a hover on a skill link showed its tooltip;
  - a search narrowed to units found units only, and the index's filter counts equal the export's.
- **Without the data:** with `OME_SITE_GAMES` empty the site builds without the database (18 pages); with the export
  missing the build stops and says where to copy it.

### 2.3 Where it departs from the design, and why

- **The list's rows are in the page**, not in a JSON file (site §8.3). The page reads without scripts and adds no
  files (§1.2's file count), and 1,318 rows filter quickly in the browser.
- **A value that stands for something (a race, a category, an element) shows as the number the game stores.** OME's
  registry names no such values, so the export cannot. The list page says so. Names for them are a registry and
  export change first (site §3.2).
- **Field labels are made from the export's names** (`granted_skill_id` reads "Granted skill"; `src/lib/labels.mjs`).
  Words for people are not in the export.
- **Slugs are the Japanese names**, the export's only language. When English text arrives they may change; the 404
  page sends an old one to the new.
- **The thumbnail a kind uses** is the site's choice, by picture name, in `site.config.mjs`. The smallest picture would
  give some units their walking sheet.
- **No language switch.** The export holds Japanese only; the switch comes with a second language (OME's export
  milestone 7).
- **Pictures are the export's PNGs**, not WebP (site §8.9 allows either).
- **The modder panel names no reference page yet:** those come with milestone 3.

### 2.4 Found while building

- **The export lacked the names of an array's elements**, which the registry has: a unit's 14 stats were 14 bare
  numbers, and modder mode could not write `stats.max_hp`. OME's `feature/data-export` now writes them, as the `field`
  table's `columns` (OME's export plan, §5).
- **Pagefind keeps a URL percent-encoded** (`/kamidori/item/1/%E9%8A%85…/`), and the built pages' paths are not; the
  check decodes the index's URLs.
- **Starlight's content styles put a top margin on every second sibling**, flex items included, which misaligned the
  switches and the pictures. Their containers carry Starlight's `not-content` class.

## 3. Milestone 5, first part: the eight tables of OME's export milestone 2

Built 2026-11-21 on `feature/kamidori-more-kinds`, off `feature/kamidori-database`. OME's export milestone 2 (its
plan, §4.1) adds eight kinds: quests, recipes, conditions, stages, dig tables, character profiles, objectives and
glossary entries. The pages, lists, filters and tooltips are generic, so they show them as they are. What the site
learned:

- **A title that is a reference.** The export's `kind.title_field` may name a reference field: a recipe is named by
  the item it makes. `readExport` takes the target's title and slug after linking the references, and the target's
  thumbnail when the entity has none of its own, so a recipe list shows the item's icon.
- **No title.** `title_field` may be null (a dig table has no name), and the page reads "Dig table 12", as it already
  did for an empty name.
- **A negative reference value is none**, as 0 is, in the infobox's "At 0 or none" line (the stages write -1 for no
  required unit).
- **Thumbnails:** a quest's list shows its requester icon (`site.config.mjs`).

Results: 3,566 pages, 3,536 entities, every one built with its search entry and tooltip; one page of each new kind
looked at in a browser.

## 4. Milestone 5, second part: the stage enemies

Built 2026-11-21 on `feature/kamidori-more-kinds`. OME's export milestone 3 (its plan, §4.2) runs the game's stage
loaders and publishes each stage's enemy table under the stage. The export gives it three new things: the `loaded`
and `loaded_field` tables, the rows in a table named `<kind>.<name>` (`stage.enemy`), and references from the stage
written `enemy.unit_id`.

- **`readExport`** reads each kind's loaded tables (their fields as `field`'s) and each entity's rows into
  `entity.loaded`, by the table's name.
- **A stage page** has a section for each loaded table that has rows, named by the table (`Enemies`) and listed under
  "On this page": a table of one row per record, by record number. Nothing in it is Kamidori's; any kind with loaded
  tables gets one.
  - **The reference columns come first.** In the registry's order the unit was the eighth column, behind a scroll;
    the reference names what a row is.
  - **A column at 0 or none in every row is left out** and named under the table, as the infobox names its zeros. An
    array shows its elements that are not 0 when most are, and a cell whose elements are all 0 is empty.
- **A unit's page** lists the stages it appears on, under "Stages: enemy unit", from the references; nothing new was
  needed for that.

Results: 3,566 pages and 126,636 links, all resolving; stage 52's page shows its 16 enemies, slot 1 the edit
APPEND02 makes, and the unit's page links back.

## 5. Milestone 5, third part: the modder panel in full

Built 2026-11-21 on `feature/kamidori-more-kinds`. OME's export milestone 4 (its plan, §4.3) fills the `snippet` and
`script_use` tables, gives `script_use` an `addresses` column, and puts the loaded tables' cells in `cell`, written
`<table>.<field>` with the index the record times the field's width plus the element.

- **The modder panel** keeps a kind's cells as they were and gives each loaded table its own list, by record and
  field, under the header a data file writes for the record (`[stage.52.enemy.r]`). The data file comes last, with a
  line on what it sets and a link to the data files guide.
- **The scripts are listed on the kind's page, not on each entity's** (design §8.7 says "the scripts that read or
  write the record"). The export counts them per table: a scene reads a record through an index, which names the
  table, not the record. 400 scripts use the unit table; on each of 445 pages that would be most of the page. The
  kind's page shows them in modder mode, most used first, with their reads, writes and indexes, and gains the modder
  switch; each entity's panel gives their count and links there.
- **The arrays no field names** (design §8.7's "later") are not in the export: OME measured none on Kamidori (its
  plan, §4.3).

Results: 3,566 pages and 133,708 links, all resolving. Stage 52's panel lists its enemies' cells under
`[stage.52.enemy.1]` to `[stage.52.enemy.16]`, and the stages page lists the 20 scripts that use the two tables.

## 6. Milestone 3: the reference pages

Built 2026-11-21 on `feature/reference-pages`, after `feature/kamidori-more-kinds`. The user left the choice between
this and OME's export milestone 6 to me ("Either milestone 3 or 6 are fine, your call"). It comes first because it is
the first reader of OME's reference bundle (OME's export milestone 5, `65bbfb85`), so what the bundle's format lacks
shows before a release publishes it.

### 6.1 The plan

- **The bundle is the one source** (site §10.2). `src/lib/bundle.mjs` opens `OME-reference-<version>.zip`, checks its
  `bundle.json` (format 1, every file's hash, no file unlisted) and reads its files from memory. Where it comes from,
  first found first:
  1. `OME_BUNDLE`: a zip, or a folder holding one;
  2. `OME_CHECKOUT`: an OME checkout, whose own `tools/reference_bundle.py --output` the build runs into
     `bundle/checkout/` (Python from `OME_PYTHON`, else `py -3.11` on Windows and `python3` elsewhere);
  3. a zip in `bundle/`, as the deploy will download one;
  4. the checkout `site.config.mjs` names (`../age-reimpl`), as in 2.
- **The guides, the games and the version come from it**, not from the checkout's files: `docs/modding/**`,
  `games.json` and `bundle.json`. A guide's link to a generated reference goes to the reference page that replaces it
  (`global-reference[-<game>].md` to the game's globals, `patch-point-reference[-<game>].md` to its patch points).
  A link to another OME file goes to it in OME's repository at the bundle's commit; only a bundle built from a
  checkout can check that the file exists.
- **The reference pages** (site §7.2, §4's paths) are Astro routes under `src/pages/docs/`, built with
  `StarlightPage` as the database's are:
  - `/docs/reference/opcodes/` and `/docs/reference/opcodes/<op>/`: an opcode's name, operands and their access,
    what it does, its control facts in the port, and for each build (4.24J, 4.33G, 4.38D) whether the game's scripts
    use it and the evidence for it;
  - for each game, `/docs/<game>/` and its sections: `globals/<name>` (address, type, meaning, the record tables it is
    a field of, the scripts that use it), `tables/<table>` (fields, what a data file may set of each from the base
    mod's shape, references, old names, scopes, the database's list of the kind built from it),
    `patch-points/<name>` (script, sites, the events at it), `events/<name>` (points, fields) and `scripts/<name>`
    (its note, its base for a layer, calls, callers, preloads, globals, patch points, waits).
  The registry's curated entries without a name (Himegari has 27) are listed on the globals page, with no page.
- **The sidebar** gains a Reference group: the opcodes, and each game's reference.
- **Links between the sections:** the database's script lists and table names link the reference; a table's page
  links the database's kind.
- **The check** (`scripts/check-site.mjs`) also checks that every opcode, named global, table, patch point, event and
  script of the bundle has its page.

### 6.2 Built

- **`src/lib/bundle.mjs`** finds the bundle (§6.1's order) and opens it: `fflate` (MIT) unzips it in memory, and
  `bundle.json` must be format 1 and hold the SHA-256 of every other file, each of which matches. From a checkout it
  runs the checkout's own `tools/reference_bundle.py --output bundle/checkout/`, so a preview reads the format a
  release publishes; the site check, after the build, reads the zip the build left there.
- **`src/lib/ome.mjs`** reads the games from `games.json` and copies the guides from the bundle's `docs/modding/**`.
  A guide whose page would be `/docs/reference/` or `/docs/<game>/` stops the build: the reference pages own them.
- **`src/lib/guide-links.mjs`** maps a guide's link to a generated reference by the paths `games.json` names for each
  game (`references`, below), and a link to another OME file to the repository at the bundle's commit.
- **`src/lib/reference-model.mjs`** makes the model of every page from the bundle and imports nothing of Astro, so
  `scripts/check-site.mjs` builds the same model; `src/lib/reference.mjs` reads it once per build. The events'
  TOML is read with `smol-toml` (BSD-3-Clause), now a direct dependency.
- **The pages**, under `src/pages/docs/`: `reference/` (the front page), `reference/opcodes/` and its 548 opcodes,
  and for each game `/docs/<game>/` and the index and entries of `globals/`, `tables/`, `patch-points/`, `events/`
  and `scripts/`. `src/components/reference/Prose.astro` shows the registries' text (paragraphs, `code`), and
  `Names.astro` an event field's cell with each global's name linked.
  - An opcode: its summary, what is left to confirm, its operands (role, types seen, access, by build where the
    access differs), the port's control facts in OME's words (`tools/opcode_flow.py`), and for each build whether
    its scripts use it and how many evidence items name it, then the evidence and OME's details.
  - A global: cell, type, category, values, meaning, confidence and source, whether the base mod exports it, its
    named columns, the tables it is a field of, and the scripts that read, write or index it.
  - A record table: records, how a data file names a record and a field (through the scope for a table a loader
    builds), each field's global, type, what it refers to and what a data file may write (the base mod's shape's
    words), old names, and the database's list of the kind built from it.
  - A patch point: its script, its site in each revision (the indexed one marked), and the events raised at it. An
    event: where it is raised and each field's cell, type and whether a handler may write it.
  - A script: id, size and fingerprint, OME's note (its base script's, for a layer), the arguments its caller sets,
    its callers, calls, computed calls and preloads, its layers, the globals it uses with the cells no global names,
    its patch points and its waits.
- **The sidebar's Reference group:** the front page, the opcodes, and each game's sections, collapsed.
- **The database links the reference** (site §8.7): the modder panel's table, each field (to its global) and each
  writer (to its script), a loaded table, and the kind page's script list and tables.
- **The check** finds a page for every opcode, named global, table, patch point, event and script, each in the
  search index, and checks that every link to a file in OME's repository names the bundle's commit.

### 6.3 Where the build departs from the design

- **Routes, not generated Markdown** (site §11 says the build writes the reference pages into
  `src/content/docs/`). The pages are Astro routes rendered from the bundle's data, as the database's are. Some 4,000
  Markdown files would pass the registries' text through a Markdown parser it was not written for, and through the
  content store's cache, whose staleness is found below.
- **Index pages** the URL map (site §4) does not list: `/docs/reference/`, `/docs/reference/opcodes/`, `/docs/<game>/`
  and one for each section of a game.
- **A script's page drops `.BIN`** (`/docs/kamidori/scripts/ADDEXP/`), as OME's notes name scripts; a layer keeps its
  prefix (`$1$ITINIT`).
- **A global without a name has no page.** Himegari's registry has 27; its globals page lists them by address.
- **"Each build's facts side by side"** (site §7.2) is what the bundle has by build: whether the build's scripts use
  the opcode, its evidence, and an operand's access where it differs by build. The port's facts are one set.
- **Versions** (site §7.3) are not built: the site reads one bundle.

### 6.4 Found

- **Astro's content store kept stale guide links,** since milestone 1. It keeps a Markdown file's render while the
  file's text is the same, and a guide's links depend on more than its text: the commit a link names, and now the
  reference targets. A build after a new OME commit still linked the old one (the supported-games page linked
  `ea91c842`), and the generated-reference links had not been mapped at all. Each copied guide now carries
  `omeLinks`, a hash of everything the rewriter reads (`guideLinkKey`, declared in `src/content.config.ts`), and the
  check refuses a link to OME's files at another commit; it found the 8 stale links before the fix.
- **The bundle lacked the paths of the generated references,** so the site kept OME's rule for their names
  (Himegari's have no suffix). OME's `games.json` now names them, each game's `references` (`globals`,
  `patch_points`), on OME's `feature/data-export` (`df43545b`), before any release published the format; OME's
  `tools/paths.py` names both files for its own tools too. Nothing else the pages show needed a change to the bundle.

### 6.5 Results

- From the bundle of OME `df43545b`, with Kamidori's export: 7,598 pages, 4,048 of them under `/docs/` (the
  guides, 4,012 reference entries and their index pages); the check passes, with every reference entry in the search
  index. The build takes about 50 s on this machine, half of it Pagefind.
- `/docs/` is 144 MB, 35 KB a page on average, mostly Starlight's sidebar, which every page repeats. Static hosts
  limit files more than bytes (site §10.3); the reference adds about 4,000 files.

## 7. Milestone 5, fourth part: script relations

Built 2026-11-21 on `feature/script-relations`, after `feature/reference-pages`. OME's export milestone 6 (its plan,

## 8. Milestone 5, fifth part: languages

Built 2026-11-22 on `feature/languages`, after `feature/script-relations`. OME's export milestone 7 (its plan, §4.6)
writes the `text` rows in each language a package gives, and `build_info`'s `languages` and `language_packages`.
Kamidori's export holds the converted English package (local test data, never in either repository).

- **The export's reading** keeps the game's text by field and each language's beside it (`translations`), and each
  entity's name in each language that has one (`names`); a recipe takes its target's names as it takes its title.
  A text the language lacks has no row, and shows in Japanese.
- **Both languages are in the page,** each element marked with its language (`data-ome-text`); the switch, "Game
  text" beside the other database switches, sets `data-ome-lang` on `<html>`, remembered in the browser and restored
  by the head script before the first paint, and the styles hide the other language. With none chosen it shows
  English, the first language the export translates into. A text with no translation is not marked and always
  shows.
- **Names** (site §8.6): links and lists show the chosen language's name, and the tooltip gives the other below it,
  in the chosen language's text line. The entity page's title shows the chosen name with the other beside it, small;
  Starlight's `PageTitle` is overridden for it, the page passing its names in `Astro.locals`. The search index takes
  each name once ("銅の魔鍵 Bronze Key"), and both languages' text. A kind's list filters on either name.
- **The credit:** a page that shows a translated name or text, its front page and each kind's list name the
  language package, its version and its authors: "English game text translated by Aroduc, from the language package
  …". A package with no authors is credited by its name, the translation called its translators' work. The converted
  package named no authors; the user named the translator, Aroduc (2026-11-22), now in its `authors`.
- **The game's front page** says the text is the game's own, with its translation where a package has one.
- **The site check** adds a rule: the page of each entity whose tooltip has a translation credits a package.

Results: 7,602 pages, the site check passing; all 1,318 items, and each kind's entities whose name or text the
export translates, carry English names in their tooltips. A headless browser run showed English by default, Japanese
after the switch and again after a reload, and each tooltip in the chosen language with the other name below.

Limit: the styles assume one translation language, as Kamidori has. With two, choosing either would show both
translations, and a text the chosen one lacks would show the other's in place of the Japanese; the styles would then
need a rule for each language and a mark, on each element, of the languages it holds.

## 9. The design pass

Started 2026-11-22 on `feature/design-pass`, after `feature/languages`, when the user had looked through the built
site ("we're probably gonna wanna do a design pass before publishing"). The user is still going through it; each note
and what it led to:

- **"The entity list pages have massive margins, so everything is pretty squished in the center."** A kind's list
  takes the page's whole width: its page lifts Starlight's content width, and on a wide screen the table fills it (on
  a narrow one it stays a block that scrolls). The user: more room "could support" stat columns to compare and
  filters such as only the units that can join, "not saying we need filtering or column variation now". The rows'
  text is centred on the thumbnail.
- **"We dont need next/previous at the bottom for entity lists, the sidebar is omnipresent."** No database page
  (the front page, a list, an entity) has the previous and next links.
- **"Tooltips stick around even after no longer being hovered."** The tooltip box's inline `display: flex` won over
  the `hidden` attribute that was meant to hide it, so it never hid once shown (since §8.5's tooltips). It is hidden
  with its own `display` now.
- **"Recipes … list out ingredient items and ingredient quantities as separate sections of a weird psuedo-table."**
  OME's declarations may now group a kind's fields (its export plan §5): rows of cells of one width, which the
  infobox shows as one table, a column for each field (its words in common with the others left out) and a row for
  each element that is not none in every field, named by the first field's column names when they say more than a
  number. Kamidori groups a recipe's ingredients (item, quantity), a quest's reward items, a unit's stats with their
  growth and caps (a row for each stat), a unit's drops (item, chance), a stage's objective rewards and a dig table's
  slots (item, roll threshold). An empty reference in a group's row shows as a dash. A value's markup (a link, an id
  no entity has, or text) is one component, `Value.astro`, for the infobox, the groups and the loaded tables.
- **"'Visible forbidden flags' and 'Unlock story flags' … the numbers shown dont really mean anything, so those would
  be better as modder mode things."** OME's declarations no longer publish any of Kamidori's story flags or scene
  numbers (a quest's, a recipe's, a stage's and its enemies', a dig table's, a character profile's, an objective's,
  a glossary entry's unlock scenes); the modder panel lists them with every cell a script wrote.

The second notes, the same day:

- **"I'd probably leave out 'at 0 or none' stuff."** Neither an entity's details nor a loaded table lists the fields
  that are 0 or none any more; they are simply left out (the modder panel still lists every cell).
- **"The overview could probably look better … Right now it's just bullet points."** The user had no design in mind.
  A game's front page now shows its kinds as cards, each with a picture of the first entry that has one (a thumbnail,
  so never an explicit picture) or the kind's initial, its name and how many entries it has; where the data comes
  from follows under "About the data".
- **"Instead of kamidori being a top level link, it should be 'Game Databases' or something, with a dropdown."** The
  header's sections are "Modding guide" and a "Game databases" menu listing each game; it closes on a click elsewhere,
  on Escape and when the focus leaves it. Starlight clips the title's box, so where the sections show (72rem and
  wider) the site lifts the clip.
- **"More things tableized properly … a reusable table component."** `DataTable.astro` draws every table of an
  entity's values: a group, an array whose elements have names, and a loader's table. A column of numbers aligns on
  the right. An array with named elements is a table of them, its 0 elements left out (Kamidori's 0 is neutral even in
  an element resistance, `－－`); an array with no names stays a list. OME's groups may now mix widths (its export plan
  §5): the narrowest field gives the rows, and a field some times as wide gives that many columns, so a condition's
  turns, stat changes and resource changes are one table of its five levels. A table with named rows whose fields
  give more columns than rows turns round, by the group's shape so every entity of a kind reads the same way: a
  condition shows its levels across and its stats down. A column that is none in every row is left out.
- **Entity pages take more width** too ("Go with giving entity pages more width", after I named a stage's squeezed
  enemies table as a rough edge). `WidePage.astro` lifts the content width on a list and an entity page; on an entity
  page the "On this page" column, which Starlight widens to centre a page of its content width, keeps the left
  sidebar's width, and the content takes the rest. `--sl-content-width` itself is left alone, since the header
  centres the search over it and the search would move between pages. The infobox and the text table span the
  content's width (since the third notes, below), so their labels line up from one table to the next.

The third notes, the same day, closing the user's pass ("I think that's it for my pass"). The OME side of each is its
export plan's §5, "The design pass's second batch":

- **"Stage objective rewards should have the objective text."** A group's rows may take labels from a loaded table's
  text (OME's `group_label`), so a stage's objective rewards are named by each objective's condition, in the language
  shown (100% Control, Stage Clear, …); the table that holds them is shown only there.
- **"'Labyrinth' … maybe we add a labyrinth entity or at least get the location name instead of an id."** OME exports
  the world map's areas as a kind, "World areas" (labyrinths and towns, with their picture, type and travel days), so
  a stage's labyrinth and a unit's habitat areas are links. Yuidora Mine lists 81 units by habitat, many of them late
  bosses with no other area: that is what the game's data holds (INFO5 draws these ids as area names).
- **"Check if conditions have a icon of some sort."** They do: 15-pixel cells of a sheet, which OME cuts out (a sheet
  picture). A condition's list and page show its icon; a picture of 32 pixels or less is drawn larger with its pixels
  kept sharp (`img.ome-pixel`). Death and the three drains have none.
- **"Some entity details may want their own simpler explanation tooltip."** OME's notes: a line for a field, a group,
  a text or a loaded table's column, which the label shows dotted with the note in a box under it on hover or focus
  (`Label.astro`; the browser's title without scripts, and the note read after the label by a screen reader). Its
  box is the page's own, apart from `tooltips.js`, which other sites embed.
- **"Maybe we drop dig tables or merge them into stage data."** OME dropped the kind; its stage maps backlog item keeps
  where a dig site is, which the page could not say.
- **"Quest text should be a table."** An entity's text is a table now: a row for each text field, or for each block
  of lines the game draws together (OME's `text_block`): a quest's overview, clear condition and failure condition.
  Only the language shown is drawn, so no row takes Starlight's margin between blocks.
- **"We know units (player controlled ones) have title changes, so we should add a table for that to unit
  entities."** A loaded table with no scope, built for each unit and each title: a unit's "Title changes" table lists
  each title with its level (-1 when a story event gives it, as its note says), the party cost and capacity changes,
  the stat and cap changes and the resistance changes by name ("Max HP +5"), and the skills it puts in each slot. A
  column of such self-naming items stacks them one to a line. Its sentence says how many rows the runs gave, not "of
  the table's records", since each run builds one record.
- **Stage maps and costumes** are on OME's backlog, as the user asked for the maps ("We can backlog this and think more
  on it later"); costumes need a loader that runs COINIT for each costume.

## 10. The usability review

The user's idea at the end of their pass ("it would help to dispatch an independent subagent to do a similar
usability/readability/etc review"), run on 2026-11-22 ("Go ahead and launch the review agent"). A fresh agent had none
of the user's notes or mine: only what the site is and who reads it, starting pages, the screenshot script, and what
was already planned (stage maps, costumes, list filters, the habitat data). It looked at 1440, 1024, 768 and 390
wide, in modder mode, in Japanese, in the dark theme and by keyboard, and scanned 66 pages for overflow. It found 22
things, ranked:

- **Broken:**
  1. On a phone the infobox of most units, stages and conditions widened the page past the screen, which pushed the
     header's menu and search off it.
  2. The modder panel's data file did not scroll, and widened the page to 4,000 px.
  3. A playable unit's page was 1.3 to 2.8 MB, almost all of it the title changes' 1,000 skill flags per title in
     the modder panel, which every visitor downloads.
  4. The home page said the database "is not built yet" and linked none, and a phone had no way to it but search.
- **Confusing:**
  - coded values shown as numbers (Sex 1, Race 1, Title level -1, a cap of 0, growth 120), down to the list filters;
  - engine fields in the player view (the sort key first, masks, an enemy's routines and divisor, allies among the
    enemies);
  - names that repeat with nothing to tell them apart (a third of the units, 50 stages, 41 objectives);
  - "Referenced by" headings that read as joins, without a drop's chance or a stage's floor;
  - the scripts' wording ("6 of the table's 30 records"), the revision on every page, and "Joins in" naming scripts;
  - a modding guide that starts from a source checkout, with repository paths as link text;
  - search results that do not say their kind, and mix the database with the reference;
  - the language switch missing the tab title, picture text and the credit line;
  - wide tables that hide columns without a sign;
  - one thing named two ways ("Cold" and "Ice", ranks in Japanese and in English);
  - a quest's "Requester" picture that is an item's.
- **Polish:**
  - the game window's line breaks kept in prose;
  - an address without its slug a 404 (the 404 page already sends it on in a browser, which plain HTTP requests do not
    run);
  - the kind cards without a line on each kind;
  - boilerplate above each page's content;
  - tooltips that Escape does not close;
  - the opcode index breaking names;
  - the home page's games table naming each guide by its id.

The four broken ones are fixed (the user: "Go ahead with the fix first"):

- **The infobox and the text table lay out fixed:** the column, not a row's content, sets the widths, so a table in a
  row scrolls in its own box. Below 40rem a row's label stands above its value. Yuela's page stayed 14 px too wide:
  a noted label's screen-reader copy is absolutely placed, and with no positioned ancestor it escaped its table's
  scroll box. The label is positioned now. A hundred entity pages, eight of each kind or more, measure 390 on a
  390 screen, and the pages tried at 1024 and 1440 fit too.
- **The data file scrolls in its box** (`.ome-snippet`).
- **The modder panel lists a run of an array's cells that one script wrote alike as one row**, "`skill_learn_flags.0`
  to `skill_learn_flags.999` (1000 cells)", with its first and last address, so every cell is still listed. Unit 1's
  panel went from 11,528 rows to 558, its page from 2.8 MB to 179 KB; no entity page is over 300 KB (the median was
  37 KB), and the database from 184 to 149 MB. Loading the panel only in modder mode is not needed at these sizes.
  The panel's sentence for a loaded table with no scope said its records were `[.1.title_change.r]` in a data file,
  which no data file reaches; it says so now.
- **The sections are reachable everywhere:** the home page's hero and games table link each database, and its last
  section lists them; below 72rem, where the header hides the sections, the sidebar shows them above its own list,
  which is the phone's menu too (`Sidebar.astro`; the guide's sidebar had no way to a database, nor a database's to
  the guide). The 404 page names the guide and each database. One list of sections serves them all
  (`src/lib/sections.mjs`).

The other eighteen wait for the user's decisions.

### 10.1 The player view: coded values, engine fields and the scripts' wording

The user's decisions on three of the confusing ones, 2026-11-22: value meanings go in OME's registry ("That's fine"),
allies get a table of their own ("Sure, give allies their own table"), and the rest as recommended ("I'm fine with
your recommendations"). OME's export plan §5 ("The player view") has what the export gives; the site reads it:

- **Values read as the game names them.** A field whose global the registry names the values of shows the name: the
  game's own in each language the export has it in, which the language switch picks as it does a name (a race,
  an element, an item category, a craftsman rank), else OME's word ("Male", "Yes", "Until cleared"). A number reads
  with its scale, offset and unit ("0.12" growth a level, "15%", "3 days", "1 turn"); a mask lists the named values
  whose bits it sets ("Normal, Hard"), and one with no bit set in a loaded table's row shows a dash. The list pages'
  columns and filters show the names too; a filter's options are plain text, so the page's script sets them in the
  chosen language. `src/lib/values.mjs` (`valueItems`, `formatNumber`) does it for every view.
- **Labels from the export** name a field where its own name reads as the game stores it ("Min range", "Boss stage",
  "In the bestiary"); `labels.mjs` makes the rest from the names, as before.
- **Engine fields are gone from the player view** (the export no longer publishes them), so the modder panel alone
  lists them.
- **Allies.** A loaded table with parts shows a table for its rows in no part and one for each part, with its note: a
  stage's "Enemies" and "Allies". "Referenced by" groups a unit's references by the part ("Stages: ally unit"). The
  modder panel keeps the table whole, headed "Cells of its enemies and allies", and says which records are allies in
  the table's own terms.
- **The scripts' wording is gone.** A loaded table has no sentence but its part's note. The game data revision is at
  the foot of an entity page and a list page, not in the line under the title. "Found in scripts" left the player
  view (site design §8.2 has the relations on the page): the modder panel's table of the calls that name an entity already lists each call, with its offset and count.

The lists' intro no longer says that coded values show as numbers.

### 10.2 Names that read apart, and what a reference means

The user approved both on 2026-11-22. OME's export plan §5 ("Names and links that read apart") has the declarations;
the site reads them:

- **A repeated name takes its qualifiers.** Where entities of a kind share a name in a language, the name takes the
  kind's qualifiers whose text differs among them, in the kind's order, until each reads apart: "Wilfred Dion (Novice
  Alchemist)" and "Wilfred Dion (Alchemist)", "Southern Shore (Floor 2)", "Get promoted to the next rank! (Ch 1)".
  A qualifier reads as the infobox shows it: a text's first line, the name of what a reference names (a stage's
  labyrinth), a value's name, a number with its label; one the translation lacks reads in the game's language. Where
  none tells them apart, the id does ("Aquarium (#333)"). A name is told apart only in the languages it is shared in:
  立方水槽 and 淡水魚の水槽 differ, and both are "Aquarium" in English. The game's own language takes full-width
  brackets, "ウィルフレド・ディオン（新米職人）". The title, the links, the lists, search and the tooltips take the name
  told apart; a URL's slug is still made from the name as the game has it, so no address changed. A recipe takes the
  name of the item it makes, told apart already. No name is shared any more, in either language.
- **"Related" replaces "Referenced by",** and each list is headed by what the reference means on the page ("Dropped
  by", "Ingredient in", "Enemy on stages", "Ally on stages"); a reference with no heading keeps the old form
  ("Units: drop item"). Where the export names details, the list is a table of the referring entities with the
  details beside each: a drop's chance, a quest's reward quantity, a stage's labyrinth and floor, an enemy's levels.
  A name there leaves out the qualifiers the table shows as columns, and an entity that refers so more than once
  alike has a count (an enemy in several slots).

`qualify`, `nameWithout` and `referencedBy` in `src/lib/values.mjs` do it. The source language moved to
`src/lib/language.mjs`, so the export reader can take the value model without the two importing each other.

## 11. The project's name and its domain

The user, 2026-11-22: with the engine one part of several, the project as a whole is **Open Maid**, "the Open Maid
project" in prose. "Open Maid Project" was set aside because its acronym is the pack format's, OMP. The user

(`docs/remake-architecture-and-roadmap.md`, "The project's name"). On the site:

- **The title and the address.** `site.config.mjs` gives the project's name, `title: 'Open Maid'`, which Starlight's
