# Site plan

**Design:** `docs/specs/2026-11-21-site-design.md` (accepted 2026-11-21), cited below as "site §n". This plan keeps what
each milestone built, what it found, and where the build departs from the design. The design stays as accepted.

**Status:** milestones 1 and 2 built on 2026-11-21: milestone 1 on branch `feature/skeleton`, milestone 2 on
`feature/kamidori-database` after it; milestone 5's first three parts (§3 to §5) on `feature/kamidori-more-kinds`
after that. The user chose milestone 1 as next ("Your call"),
ahead of OME's export milestone 2, because the stack was the design's largest unverified choice.

## 1. Milestone 1: the skeleton, and the trial of the stack

### 1.1 What it built

- **The project:** Astro 7.4.13 with Starlight 0.43.1. Pagefind 1.6.0 comes with Starlight. It needs Node 22.23.4 or
  later; the trial ran on Node 24.11.1.
- **The guides** (site §7.1). `src/lib/ome.mjs` copies OME's `docs/modding/` from a local checkout into
  `src/content/docs/docs/`, which git ignores:
  - a guide's first `# ` heading becomes its title;
  - a `README.md` becomes its folder's index page.

  `astro.config.mjs` runs the copy each time the config loads, so `astro dev` and `astro build` both start from the
  checkout.
- **The sidebar** follows the guide index's "Where to go next" table, which is OME's reading order. The game guides
  form their own group. A guide the table does not name is listed after the table's, with a warning.
- **Link mapping** (site §7.1): `src/lib/guide-links.mjs`.
  - A guide's link to another guide goes to that guide's page.
  - A link to an OME file outside the guides goes to the file in OME's repository, at the checkout's commit. Nine
    links do: the generated global and patch-point references, and `adding-a-game.md`. Site milestone 3 maps the
    references to reference pages instead.
  - Any other relative link fails the build, naming the guide and the link.
- **Home** (site §6): `src/pages/index.astro`, built with Starlight's `StarlightPage`, so it shares the header, the
  search and the look. It holds:
  - what OME is;
  - the games, with their support levels and the maker's site, from the profile manifests;
  - a link to OME's latest release;
  - a line on the database to come.
- **The age notice** (site §8.10): `src/components/AgeNotice.astro`, placed in every page through an override of
  Starlight's `SkipLink`.
  - It is a dialog that the page opens already shown.
  - Its button closes it through `<form method="dialog">`, so it works without scripts.
  - With scripts the dialog is modal, and the confirmation is remembered in `localStorage` (`ome-age-confirmed`).
  - A head script marks a confirmed visitor before the first paint, so the notice never flashes for them.
- **The check:** `scripts/check-site.mjs` runs after every `npm run build` and exits 1 on any failure.
  - Every link and asset a page names on the site must resolve to a built file, and every anchor to an id on its
    page. This also checks the guides' anchors against the headings Astro actually built.
  - The search index must hold exactly the pages that mark their content for search.
- **`site.config.mjs`** (site §11 names it `site.config`). It holds:
  - the placeholder domain;
  - the checkout's path (`OME_CHECKOUT` overrides it);
  - OME's repository.

  It is JavaScript so that it can carry comments and read the environment.
- **The favicon** is a copy of OME's icon (`godot/assets/ome-icon.svg`, drawn for OME, MIT). Starlight links
  `/favicon.svg` from every page; the check found it missing.

### 1.2 The trial's results

The design's "not verified" items (site, header):

- **Versions.** Astro is at 7, as the research note said. One thing it did not foresee: Astro 7's Markdown processor
  is Sätteri, a Rust parser, not remark. A plugin is a Sätteri mdast plugin (`markdown.processor: satteri({
  mdastPlugins })`), and Starlight adds its own plugins to the same processor.
- **One project, one search index: verified.**
  - Starlight serves `/docs/`, and the home page is an ordinary Astro page.
  - Pagefind indexes every built page that marks its content for search, and `StarlightPage` marks it.
  - In headless Chrome, a search for a word only on the home page, typed into the header's search on a guide page,
    returns the home page. Guide words return the guides.
- **Scale.** A temporary route of 4,000 entity-like pages, each built with `StarlightPage` and a table of 24 linked
  fields, gave these numbers:
  - 4,018 pages built in 17.6 s, Pagefind's 3.3 s included;
  - 72 MB in 8,106 files;
  - the check walked 121,162 links.

  The route was removed.
- **File count (site §10.3).** Pagefind writes one fragment file per page, so the site has about two files per page.
  §10.3 estimated 5,000 files for Kamidori; it is nearer 8,000 before pictures, and three games pass Cloudflare's
  20,000 even with pictures on an asset host. The deploy milestone chooses the host with this number (§1.4).
- **The age notice in a browser.** Checked in headless Chrome:
  - on a first visit the notice is modal and nothing is stored;
  - Escape leaves it open;
  - the button removes it and stores the confirmation, and the next page has no notice;
  - with scripts off the notice shows, and its button closes it.

### 1.3 Found while building

- **Escape.** Chrome closes a modal dialog on Escape before the visitor has touched the page, whatever a `cancel`
  handler does. The first version took that close as a confirmation. Now only the button's value (`confirm`) counts,
  and a notice closed any other way opens again.
- **Starlight leaves a page out of search when its route ends in `/404`.** It takes such a page for a 404 page. The
  database's URLs end in the entity's slug (site §4), so an entity is affected only if its slug is `404`. Milestone 2
  must make sure no slug is `404`.
- **Data for a page goes through the virtual module `virtual:ome`.** In a built page, `import.meta.url` names the
  bundled chunk, not the source file, so a page cannot find the checkout by a relative path. The config resolves it
  and passes the pages what they read.
- **A failed build on Windows** sometimes ends with a libuv assertion from Node (`!(handle->flags &
  UV_HANDLE_CLOSING)`) after Astro's error. The build still fails, with Astro's message printed first.

### 1.4 Left for later, and why

- **Screenshots on the home page** (site §6). They show game art, so they wait for the user's word on which pictures
  the site's repository may hold.
- **The release's packages by name** (site §6). The checkout knows its version but not the latest release's assets.
  The home page links the latest release; the bundle or the release itself can name them later.
- **Support levels by name.** The manifests hold the codes (`P3`, `M3`), and the home page shows those and links the
  games page that explains them. If the bundle carries the levels' names (OME export §8.1), the home page can show
  them.
- **Where to buy** is the manifest's `launcher.site`, the maker's site. The manifests name no store.
- **Whether OME's repository is public** was not checked (`gh` is not installed here). If it is private at the deploy
  milestone, the nine links into it (§1.1) and the release link reach no one.
- **A header link to each section.** The site title links home, and the database does not exist yet. The header gets
  section links when the database's first pages do (milestone 2).

## 2. Milestone 2: Kamidori's first kinds

Built on 2026-11-21 on branch `feature/kamidori-database`, from OME's first export: Kamidori's 1,318 items, 445
units and 452 skills, game data revision `0294c8eafacf`. The user said "Go ahead".

### 2.1 What it built

- **Reading the export.** `site.config.mjs` `games` lists each game's revision. The export folder OME writes is copied
  to `data/<game>/`, which git ignores. `OME_SITE_GAMES` overrides which games are built; empty builds the site
  without a database.
  - `src/lib/export.mjs` reads the database with Node's built-in `node:sqlite` into the pages' model: kinds, fields,
    entities, references both ways, pictures and cells.
  - The build fails on a missing export, another format version, and a picture file the export lacks (site §10.2).
- **Pages** (site §4):
  - `/<game>/`, the game's front page;
  - `/<game>/<kind>/`, a list;
  - `/<game>/<kind>/<id>/<slug>/`, an entity;
  - `/<game>/tooltips/<kind>.json`, the tooltips;
  - `/pictures/<game>/<revision>/`, the pictures, with `standin/` for the blurred copies.

  Every database page is built on `StarlightPage`, with a sidebar of the game's kinds. The header links each section.
- **An entity page** (site §8.2) shows:
  - its name, pictures (a file used under two names is shown once), kind and game revision;
  - an infobox of its published fields;
  - its text;
  - what refers to it, grouped by kind and field;
  - script relations, once the export has them;
  - the modder panel.
- **The infobox** reads values through `src/lib/values.mjs`:
  - a reference is a link with a tooltip;
  - an array's elements are named by the export's new `columns`;
  - a field at 0 or none goes in one line under the infobox;
  - an array whose elements are mostly 0 shows the others only.

  Without that, a key item's infobox was some forty rows of zeros.
- **The modder panel** (site §8.7) is in every entity page and shown only in modder mode. It names the record for OMS
  and data files (`unit[1]`, `[unit.1]`) and lists every cell a script wrote: its name as a data file writes it
  (`stats.max_hp`), its value, its writer (so its layer) and its address. It also lists the pictures' catalog names.
- **The explicit pictures** (site §8.11):
  - the build makes each stand-in with `sharp`, the picture shrunk to 12 pixels across and shown blurred at full
    size;
  - a click loads the picture;
  - the "Show explicit pictures" switch, beside modder mode's and remembered the same way, shows them all;
  - a thumbnail or a tooltip is never an explicit picture, and the site sets no preview image.
- **Lists** (site §8.3) have the rows in the page, filters on the export's filterable fields and the name, and the
  filters in the URL (`?race=3`).
- **Tooltips** (site §8.5): `public/tooltips.js` has no dependencies.
  - It shows the name, the thumbnail and a line of text, from the kind's file, loaded on the first hover.
  - On another site it shows the name and the picture only.
- **Search** (site §8.4) indexes an entity's name and text, with `game` and `kind` as Pagefind filters. Starlight's
  search box shows the filters by itself.
- **The 404 page** (`src/pages/404.astro`, in place of Starlight's) sends an entity's address without its slug, or with
  a wrong one, to the right page, using the kind's tooltip file.
- **`scripts/check-site.mjs`** also checks every entity the tooltip files list: its page is built and in the search
  index, and its picture is built.

### 2.2 Results

- **The build:** 2,237 pages in 15 s. Its output is 127 MB in 6,732 files, 45 MB of it pictures. The check walks
  59,993 links.
- **In headless Chrome:**
  - unit 331's page loaded only its stand-in until the click, then the picture;
  - the switch showed unit 52's explicit picture on load;
  - modder mode stayed on across pages;
  - `?race=3` showed 44 units;
  - `/kamidori/unit/331/` and `/kamidori/item/1/wrong-slug/` reached their pages;
  - a hover on a skill link showed its tooltip;
  - a search narrowed to units found units only, and the index's filter counts equal the export's.
- **Without the data:** with `OME_SITE_GAMES` empty the site builds without the database (18 pages); with the export
  missing the build stops and says where to copy it.

### 2.3 Where it departs from the design, and why

- **The list's rows are in the page**, not in a JSON file (site §8.3). The page reads without scripts and adds no
  files (§1.2's file count), and 1,318 rows filter quickly in the browser.
- **A value that stands for something (a race, a category, an element) shows as the number the game stores.** OME's
  registry names no such values, so the export cannot. The list page says so. Names for them are a registry and
  export change first (site §3.2).
- **Field labels are made from the export's names** (`granted_skill_id` reads "Granted skill"; `src/lib/labels.mjs`).
  Words for people are not in the export.
- **Slugs are the Japanese names**, the export's only language. When English text arrives they may change; the 404
  page sends an old one to the new.
- **The thumbnail a kind uses** is the site's choice, by picture name, in `site.config.mjs`. The smallest picture would
  give some units their walking sheet.
- **No language switch.** The export holds Japanese only; the switch comes with a second language (OME's export
  milestone 7).
- **Pictures are the export's PNGs**, not WebP (site §8.9 allows either).
- **The modder panel names no reference page yet:** those come with milestone 3.

### 2.4 Found while building

- **The export lacked the names of an array's elements**, which the registry has: a unit's 14 stats were 14 bare
  numbers, and modder mode could not write `stats.max_hp`. OME's `feature/data-export` now writes them, as the `field`
  table's `columns` (OME's export plan, §5).
- **Pagefind keeps a URL percent-encoded** (`/kamidori/item/1/%E9%8A%85…/`), and the built pages' paths are not; the
  check decodes the index's URLs.
- **Starlight's content styles put a top margin on every second sibling**, flex items included, which misaligned the
  switches and the pictures. Their containers carry Starlight's `not-content` class.

## 3. Milestone 5, first part: the eight tables of OME's export milestone 2

Built 2026-11-21 on `feature/kamidori-more-kinds`, off `feature/kamidori-database`. OME's export milestone 2 (its
plan, §4.1) adds eight kinds: quests, recipes, conditions, stages, dig tables, character profiles, objectives and
glossary entries. The pages, lists, filters and tooltips are generic, so they show them as they are. What the site
learned:

- **A title that is a reference.** The export's `kind.title_field` may name a reference field: a recipe is named by
  the item it makes. `readExport` takes the target's title and slug after linking the references, and the target's
  thumbnail when the entity has none of its own, so a recipe list shows the item's icon.
- **No title.** `title_field` may be null (a dig table has no name), and the page reads "Dig table 12", as it already
  did for an empty name.
- **A negative reference value is none**, as 0 is, in the infobox's "At 0 or none" line (the stages write -1 for no
  required unit).
- **Thumbnails:** a quest's list shows its requester icon (`site.config.mjs`).

Results: 3,566 pages, 3,536 entities, every one built with its search entry and tooltip; one page of each new kind
looked at in a browser.

## 4. Milestone 5, second part: the stage enemies

Built 2026-11-21 on `feature/kamidori-more-kinds`. OME's export milestone 3 (its plan, §4.2) runs the game's stage
loaders and publishes each stage's enemy table under the stage. The export gives it three new things: the `loaded`
and `loaded_field` tables, the rows in a table named `<kind>.<name>` (`stage.enemy`), and references from the stage
written `enemy.unit_id`.

- **`readExport`** reads each kind's loaded tables (their fields as `field`'s) and each entity's rows into
  `entity.loaded`, by the table's name.
- **A stage page** has a section for each loaded table that has rows, named by the table (`Enemies`) and listed under
  "On this page": a table of one row per record, by record number. Nothing in it is Kamidori's; any kind with loaded
  tables gets one.
  - **The reference columns come first.** In the registry's order the unit was the eighth column, behind a scroll;
    the reference names what a row is.
  - **A column at 0 or none in every row is left out** and named under the table, as the infobox names its zeros. An
    array shows its elements that are not 0 when most are, and a cell whose elements are all 0 is empty.
- **A unit's page** lists the stages it appears on, under "Stages: enemy unit", from the references; nothing new was
  needed for that.

Results: 3,566 pages and 126,636 links, all resolving; stage 52's page shows its 16 enemies, slot 1 the edit
APPEND02 makes, and the unit's page links back.

## 5. Milestone 5, third part: the modder panel in full

Built 2026-11-21 on `feature/kamidori-more-kinds`. OME's export milestone 4 (its plan, §4.3) fills the `snippet` and
`script_use` tables, gives `script_use` an `addresses` column, and puts the loaded tables' cells in `cell`, written
`<table>.<field>` with the index the record times the field's width plus the element.

- **The modder panel** keeps a kind's cells as they were and gives each loaded table its own list, by record and
  field, under the header a data file writes for the record (`[stage.52.enemy.r]`). The data file comes last, with a
  line on what it sets and a link to the data files guide.
- **The scripts are listed on the kind's page, not on each entity's** (design §8.7 says "the scripts that read or
  write the record"). The export counts them per table: a scene reads a record through an index, which names the
  table, not the record. 400 scripts use the unit table; on each of 445 pages that would be most of the page. The
  kind's page shows them in modder mode, most used first, with their reads, writes and indexes, and gains the modder
  switch; each entity's panel gives their count and links there.
- **The arrays no field names** (design §8.7's "later") are not in the export: OME measured none on Kamidori (its
  plan, §4.3).

Results: 3,566 pages and 133,708 links, all resolving. Stage 52's panel lists its enemies' cells under
`[stage.52.enemy.1]` to `[stage.52.enemy.16]`, and the stages page lists the 20 scripts that use the two tables.
